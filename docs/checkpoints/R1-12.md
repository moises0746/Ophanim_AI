# R1-12 Checkpoint — Assistant Event Stream & Live UI Presentation

## Status

Complete. Next eligible task: **R1-13 — Governed Browser Automation** (informational only; not authorized).

## Objective

Deliver a typed, workspace-scoped SSE path from Ophanim Core to the Desktop Assistant so authoritative sanitized events drive Assistant state, Activity Feed entries, and approval presentation.

## Scope delivered

- Added a typed event broadcaster and stream-authorization ports with bounded per-subscriber queues.
- Added a default-deny authorizer and an R1-05 identity-backed authorizer requiring `assistant:events:read` in the exact workspace.
- Added `GET /api/v1/assistant/events/stream` with Bearer authentication, workspace UUID validation, sanitized canonical envelope serialization, named SSE events, and no public event-authoring endpoint.
- Added a fetch-stream Desktop client that supports an injected authorization provider, named SSE frames, canonical event types, event-ID deduplication, per-scope sequence regression protection, workspace filtering, and bounded approval projection.
- Added an explicit projection from the accepted lowercase Core semantic states into the merged R1-11 uppercase presentation vocabulary.
- Wired `App.tsx` to an injected authorized stream client and removed timer-driven fabricated task, tool, evidence, approval, and completion activity.
- Kept prompt submission, approval mutation, and cancellation outside R1-12; the UI truthfully reports that no action occurred.

## Architecture impact

- Preserves `Core event -> typed delivery client -> projection -> presentation` direction.
- Core remains the only authoritative event producer; the unsafe draft `/emit` route was removed.
- Transport authorization is a port. The API defaults to deny until the composition root injects an identity-backed authorizer.
- Desktop remains presentation-only and accepts credentials through an injected authorization provider rather than embedding secrets.

## Security impact

- Stream access requires Bearer authentication, exact workspace match, and `assistant:events:read` scope when the identity adapter is wired.
- Missing authorization and the default runtime authorizer fail closed with 401/403.
- Cross-workspace, duplicate, and stale events are ignored by the Desktop client.
- Only bounded sanitized envelope/payload data is delivered; no raw prompts, credentials, hidden reasoning, or client-authored authoritative events were added.
- Queue overflow is logged and does not mutate Core state or grant approval.

## Migrations/rollback

## Known limitations

- The production composition root still needs an authorized IdentityService instance and secure Desktop credential provider; the default authorizer intentionally denies all access.
- Fan-out is in-memory and non-replayable. Durable replay/resume, retention cursors, resync markers, distributed delivery, and slow-consumer recovery remain future work.
- No existing application use case publishes into the broadcaster yet; producers must inject the port when their task is authorized.
- R1-11's uppercase visual states differ from the accepted lowercase semantic-state contract. R1-12 uses an explicit non-authoritative projection rather than introducing a second Core state model.
- Approval decisions, prompt submission, and emergency-stop/cancellation API calls are not part of this task.

## Open risks/blockers

No blocker within R1-12. Production activation remains fail-closed until identity and credential composition are explicitly wired.
