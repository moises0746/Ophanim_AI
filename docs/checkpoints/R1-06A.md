# R1-06A Checkpoint — Governed Cloud Model Provider Adapters

## Status

Complete. Recommended next task: **R1-RUN-01 — Local Runtime Composition & Desktop Chat Launcher** (informational only; not authorized).

## Objective

Allow Ophanim Core to use explicitly configured OpenAI, Google Gemini, and Anthropic Claude models through the existing capability/privacy-aware model router without exposing credentials or weakening local-only isolation.

## Scope delivered

- Added specific `openai`, `gemini`, and `anthropic` provider identities while preserving the existing generic cloud/mock types.
- Implemented OpenAI Responses, Gemini `generateContent`, and Anthropic Messages adapters behind `ModelProviderPort`.
- Fixed provider origins to official API domains; arbitrary base URLs are not accepted.
- Added execution-time `SecretResolverPort` and an exact-allowlist environment adapter for local development.
- Added model/capability/timeout/retry/secret-reference settings under `OPHANIM_*`; providers remain disabled until a model ID is configured.
- Added provider construction and sanitized health reporting through `/status/providers`.
- Enforced `STANDARD` privacy mode in both router and adapters before credential resolution.
- Added bounded transient retry, cancellation propagation, response normalization, credential rotation, malformed-response handling, and redacted errors.
- Added non-secret environment template entries and an integration configuration guide.

## Architecture impact

- Preserves `application/domain -> ModelProviderPort <- provider adapter` dependency direction.
- Provider-specific request/response schemas stay inside adapters.
- Model IDs and declared capabilities are explicit configuration rather than hard-coded moving aliases.
- Cloud model output remains untrusted analysis data and gains no tool or side-effect authority.
- No provider SDK dependency was added; adapters use the existing bounded `httpx` dependency.

## Security impact

- Credentials resolve only at request time through opaque references and are not cached by adapters.
- Credential values never enter model descriptors, domain requests/responses, Desktop code, normal logs, health payloads, or committed configuration.
- Missing/unallowlisted credentials fail before network access.
- `LOCAL_ONLY` and `PRIVATE` calls are denied by each cloud adapter before secret resolution, even if the router is bypassed.
- Only transport errors, HTTP 429, and HTTP 5xx are retried, with bounded attempts/backoff.
- Cancellation is never swallowed or retried.
- Provider error bodies are not included in raised errors, preventing reflected secret leakage.
- Provider domains are fixed to official OpenAI, Google, and Anthropic origins.

## Migrations/rollback

## Known limitations

- R1-RUN-01 is still required to expose an authenticated Core chat use case and wire the Desktop to it. The Desktop never calls providers directly.
- Production credential-store integration is not implemented; the environment resolver is local-development only.
- Model IDs, context windows, and truthful capabilities must be configured by the operator from current provider documentation.
- These adapters currently normalize text chat only. Vision, embeddings, audio, provider tools, streaming tokens, and tool-role messages are not implemented.
- Anthropic structured-output mode is not claimed; OpenAI stop sequences are explicitly rejected by this adapter.
- No live-provider, billing, quota, cost-budget, or rate-limit integration test runs by default.

## Open risks/blockers

No blocker within R1-06A. Running an end-user chat remains blocked on R1-RUN-01 runtime/API/Desktop composition and secure production credential custody.
