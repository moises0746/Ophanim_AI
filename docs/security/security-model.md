# Initial Security Model

## Protected assets

- owner identity, preferences, conversations, and memory;
- credentials, cookies, OAuth tokens, and browser sessions;
- local files, Obsidian data, and retrieved enterprise knowledge;
- desktop screenshots, clipboard content, microphone data, and transcripts;
- source repositories, cloud resources, messages, and third-party accounts;
- task history, approvals, and audit evidence.

## Trust boundaries

Treat these as separate trust zones:

- desktop UI and local user session;
- NEXUVO Core and its database;
- local model runtimes;
- AnythingLLM and indexed documents;
- external agents and cloud models;
- tool adapters and authenticated third-party services;
- browser and desktop automation sessions;
- notification channels and remote approval links.

Localhost is not automatically trusted. Authenticate mutating desktop/core communication, validate origins, and do not expose service ports to the LAN by default.

## Principal threats

- prompt injection in web pages, documents, email, chat, and tool output;
- confused-deputy actions performed with the owner's logged-in identity;
- credential or private-data leakage into prompts, logs, screenshots, or notifications;
- malicious or incorrect tool arguments generated by a model;
- duplicate side effects after retries or worker recovery;
- unauthorized expansion of delegated permissions;
- visual automation acting on the wrong window or stale screen;
- compromised provider, plugin, MCP server, dependency, or model artifact;
- audit tampering or misleading success reports.

## Required controls

- data and tool scopes bound to each task;
- capability-based tool access with deny-by-default policy;
- structured validation at every adapter boundary;
- approval records bound to an exact action digest and expiration;
- idempotency keys or read-before/write-after checks for side effects;
- protected credential injection outside model context;
- append-only audit events with content hashes for material artifacts;
- cancellation and emergency-stop checks between steps;
- explicit cloud egress policy and visible privacy mode;
- output encoding and untrusted-content separation in prompts;
- log redaction, retention limits, and user deletion controls.

## Approval risk examples

| Risk | Examples | Default behavior |
| --- | --- | --- |
| Low | Read local status, search approved knowledge | May run within task scope |
| Medium | Create local draft, download approved public file | Run or approve according to policy |
| High | Send message, upload data, modify repository, deploy | Exact-action approval required |
| Critical | Delete data, change permissions, purchase, expose secret | Deny or require strong fresh approval |

## Security work before unattended release

Create a formal threat model, credential-store implementation, local authentication design, signed update strategy, dependency scanning, encrypted sensitive storage, audit integrity checks, and incident-response procedure before advertising unattended production use.
