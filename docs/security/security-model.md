# Ophanim AI Security Model

## Security Objective

Ophanim may operate with access to authenticated applications, private knowledge, enterprise systems and production-adjacent tools. Authorization, policy, approval, credential isolation, evidence and audit are therefore core architecture, not release-time hardening.

## Protected Assets

- owner identity, preferences, conversations and memory;
- credentials, cookies, OAuth tokens and browser sessions;
- local files, Obsidian data and enterprise knowledge;
- screenshots, microphone data and transcripts;
- repositories, cloud resources, messages and third-party accounts;
- task history, policies, approvals and audit evidence.

## Trust Boundaries

Treat these as separate zones:

- desktop UI/local user session;
- Ophanim Core;
- model providers/runtimes;
- AnythingLLM/knowledge subsystem;
- MCP servers;
- browser runtime/session;
- enterprise tools/APIs;
- secret provider;
- PostgreSQL/evidence storage;
- Obsidian/private local data.

Localhost is not automatically trusted. Mutating desktop/core communication must be authenticated/authorized and services should bind to loopback by default in local development.

## Principal Threats

- prompt injection in web pages, documents, email, chat, MCP resources, logs and tool output;
- confused-deputy actions performed with the user's logged-in identity;
- credential/private-data leakage into prompts, logs, screenshots or notifications;
- malicious/incorrect tool arguments generated by a model;
- duplicate side effects after retries/recovery;
- unauthorized expansion of delegated permissions;
- browser automation acting on the wrong site/session/state;
- compromised provider, plugin, MCP server, dependency or model artifact;
- approval replay/bypass;
- audit/evidence tampering;
- misleading success reports without verification.

## Authorization Pipeline

```text
Goal
 -> Plan
 -> Capability Request
 -> Identity / RBAC
 -> Environment Scope
 -> Tool Allowlist
 -> Policy Evaluation
 -> Approval if required
 -> Credential Resolution
 -> Deterministic Execution
 -> Verification
 -> Evidence / Audit
```

No model response can skip this pipeline.

## Required Controls

- capability-based deny-by-default access;
- task-bound data/tool/environment scopes;
- structured validation at adapter/tool boundaries;
- read-only defaults;
- exact-action approvals bound to parameters/destination/environment and expiration;
- changed action parameters invalidate earlier approval;
- idempotency/read-before-write/write-after verification where side effects exist;
- credentials injected outside model context whenever possible;
- append-only audit semantics for material actions/approvals;
- evidence hashes/metadata where practical;
- cancellation and emergency-stop checks between steps;
- explicit cloud egress/privacy policy;
- prompt separation for untrusted retrieved content;
- log redaction and retention controls;
- dedicated/protected browser profiles;
- vendor-source isolation and dependency scanning.

## Prompt Injection Controls

External content is data, not authority.

- Retrieved content cannot grant capabilities or permissions.
- Model-proposed tool calls are independently validated/policy checked.
- Treat web pages, MCP resources, documents and logs as untrusted.
- Minimize secret/context exposure.
- Record source provenance for grounded findings.

## Credential Model

Agents never own credentials.

```text
Agent -> Capability -> Tool -> Secret Reference -> Secret Provider -> Execution
```

Secret values should not appear in agent definitions, source code, normal logs, prompts or audit records.

Browser cookies/storage/auth state are credentials and must be protected accordingly.

## Risk Classes

| Risk | Examples | Default |
| --- | --- | --- |
| Low | Read approved non-sensitive data | Allowed within task scope |
| Moderate | Read private enterprise/authenticated data | Allowed only by explicit scope/policy |
| High | Send, publish, upload, modify state | Fresh/exact approval required |
| Critical | Production changes, deletion, permissions, credentials/security | Deny or strong explicit approval/policy |

MVP supports Low/Moderate read-only operations only.

## Forbidden Generic Capabilities

Do not expose to agents:

- arbitrary SQL;
- arbitrary shell;
- unrestricted filesystem;
- unrestricted browser domains;
- unrestricted network requests;
- raw secret-store browsing.

Use bounded purpose-built tools instead.

## Approval Security

Approval records should include:

- task ID;
- tool/action;
- normalized parameter digest;
- destination/resource;
- environment;
- risk;
- approver identity;
- issued/expiry timestamps;
- optional rollback/verification plan.

Voice recognition alone is never sufficient authorization for sensitive operations.

## Logging and Evidence

Log:

- task/tool/event IDs;
- provider/tool identity;
- sanitized arguments/results where necessary;
- duration/status;
- policy/approval outcomes;
- evidence references/hashes.

Avoid by default:

- credentials/cookies/tokens;
- complete private documents;
- unnecessary full prompts/transcripts;
- sensitive screenshots inline in logs.

## Required Security Testing

- authorization denial tests;
- environment-boundary tests;
- tool allowlist tests;
- approval binding/replay/expiry tests;
- secret redaction tests;
- prompt-injection tests;
- MCP unregistered/untrusted tool tests;
- browser domain/action tests;
- arbitrary SQL/shell/filesystem negative tests;
- dependency/secret scanning.

## MVP Security Gate

The Transaction Investigation MVP cannot be released unless it demonstrates:

- read-only access only;
- allowlisted test applications/tools;
- no arbitrary SQL/shell/filesystem/browser access;
- audit trail for every tool call;
- evidence provenance;
- no credential leakage into normal model-visible results/logs;
- cancellation/emergency-stop behavior;
- no remediation/write action path.
