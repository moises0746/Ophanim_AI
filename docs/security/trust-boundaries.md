# Ophanim Trust Boundaries

## Boundary Rules

Every boundary below is independently authorized. “Trusted” means the side may assert only the stated contract after authentication and validation; it does not mean its content is inherently safe. External content, model output, vendor code, and client projections remain untrusted data.

| # / boundary | Trusted side | Untrusted assumptions | Auth / authorization | Data / direction | Credential handling | Validation / sanitization | Audit / failure behavior |
|---|---|---|---|---|---|---|---|
| 1. User ↔ Assistant | Authenticated user intent and Core-rendered state | User input may be ambiguous or malicious; voice may misrecognize | User/session auth; task and workspace scope; no voice-only sensitive approval | User input to Assistant; sanitized state/results back | Never expose secrets; voice/transcript classification applies | Bound objectives; no raw arbitrary commands; sanitize display | Correlate input/task; ambiguity denies or asks; UI cannot authorize |
| 2. Desktop ↔ Core | Core API/policy; desktop is a client projection | Client can be tampered with or disconnected | Authenticated local IPC/HTTP; route and capability checks | Scoped requests/events only; no hidden internals | No credentials in client payloads; opaque refs only | Schema, origin, scope, event visibility, redaction | Log correlation and denials; fail closed on auth/disconnect |
| 3. Core ↔ model runtime | Core control plane | Model output is probabilistic, compromised, or prompt-injected | Provider identity/config and data-routing policy | Minimized classified context to model; untrusted output to Core | Exclude secrets; provider credentials stay adapter-side | Structured output/tool schema validation; prompt separation | Record provider/version and outcome; timeout/degrade, never execute model claims |
| 4. Core ↔ Agent Mesh profile | Core policy and immutable profile version | Profile may be stale, overbroad, or misconfigured | Profile activation and task assignment authorization | Bounded capability/scope subset from Core to profile | Profiles contain no credentials | Validate subset, budgets, environment/data scope | Assignment/denial/version audit; reject widening or self-grant |
| 5. Core ↔ MCP server | Core registry/policy boundary | Server metadata/resources/tools may be malicious or compromised | Registered/allowlisted server identity; per-tool policy | Scoped schema-validated requests/results; discovery never grants auth | Resolve secrets only in tool runtime; never server/model context by default | Schema/version, timeout, cancellation, output redaction, prompt-injection treatment | Tool/evidence/policy audit; quarantine/deny on compromise or malformed output |
| 6. Core ↔ browser runtime | Core browser policy and isolated worker | Worker/page/session may be compromised; UI is ambiguous | Approved app/domain/profile and task/tool policy | Bounded DOM/accessibility/read actions; evidence back | Dedicated profile only; cookies/auth state are secrets | Redirect, popup, upload/download, JS, path, action, and domain checks | Navigation/action/evidence audit; stop and deny on escape |
| 7. Browser ↔ external web app | Approved application/domain boundary | Page content, redirects, prompts, and UI controls are hostile/untrusted | App/domain allowlist and session scope | Browser reads only approved scope; no unrestricted writes | No personal profile; no exfiltration through page | DOM-first; detect state-changing action; sanitize page text | URL/action/result evidence; quarantine on injection/escape |
| 8. Core ↔ AnythingLLM | Core knowledge port | Vendor service, retrieval result, workspace, or embeddings may be wrong/injected | Adapter identity, workspace/data scope, provider policy | Scoped retrieval/ingestion requests and citations back | Adapter credentials only; vendor internals not domain authority | Schema, citation, classification, prompt-injection and source checks | Retrieval/evidence correlation; degrade when unavailable |
| 9. AnythingLLM ↔ knowledge sources | Explicit ingestion scope | Documents, Obsidian, messages, and sources may be poisoned/private | User consent, source scope, exclusions, identity | Authorized source content into subsystem; citations/provenance out | Source credentials at adapter boundary | File/path/source validation, classification, sanitization | Ingestion/source audit; skip/quarantine unauthorized or malformed content |
| 10. Core ↔ approved database tools | Core tool/policy boundary | Results can be sensitive, stale, or prompt-injected; queries may be unsafe | Purpose-built allowlisted read tool and data scope | Parameterized bounded reads/results; no arbitrary SQL | DB credentials resolved in tool runtime | Typed query parameters, table/column/row scope, timeout/limit | Query/tool/evidence audit; deny arbitrary SQL and scope escape |
| 11. Core ↔ approved log tools | Core tool/policy boundary | Logs may contain secrets, attacker text, or misleading data | Allowlisted source/index/time scope | Bounded sanitized log retrieval | Runtime-only secret refs | Query allowlist, redaction, size/time limits | Correlate source/query/evidence; redact/degrade on leakage |
| 12. Core ↔ PostgreSQL | Core persistence boundary | DB, network, backups, or operators may fail/compromise | Service identity, least-privilege roles, scoped queries | Canonical state/material events to DB; authorized reads back | DB secrets outside code/agents; encryption direction TBD | Parameterized queries, constraints, transaction/integrity checks | Append/material audit; fail closed, recover from PG, never Redis authority |
| 13. Core ↔ Redis | Core transient coordination boundary | Cache/queue may be lost, replayed, or tampered | Service auth and namespace scope | Ephemeral leases/buffers only; no canonical state | Redis credentials runtime-only | TTL/namespace/value limits, idempotent consumers | Metrics/errors; loss triggers resync/recovery, not data loss claim |
| 14. Tool runtime ↔ secret provider | Approved tool execution | Provider may be unavailable or mis-scoped | Workload identity, secret reference and task/tool policy | Minimum secret material one-way into bounded execution | Values never persist/return/log; rotate/revoke centrally | Reference, scope, purpose, expiry, redaction checks | Access metadata without values; deny on ambiguity/unavailability |
| 15. Core ↔ artifact/evidence storage | Core evidence metadata | Object store/path/content may be tampered or overshared | Scoped object identity and authorization | Immutable reference/hash metadata; bytes only through approved store | Encryption/key refs outside model/events; access scoped | Hash/size/media/classification, malware/path checks | Capture/access/redaction/retention audit; quarantine integrity failure |
| 16. Development/test ↔ production | Environment boundary | Misconfiguration, copied credentials, cross-scope data | Separate identities, networks, configs, stores, and allowlists | Synthetic test data only across boundary; no production writes | No production creds in dev/test; no cross-env refs | Environment tags and startup/route/tool checks | Alert/deny cross-env use; production remains isolated |
| 17. Future voice capture ↔ Assistant/Core | Core-authorized capture state | Misrecognition, ambient speech, spoofed audio, sensitive transcript | Explicit microphone permission, session/task scope, mute/stop | Sanitized lifecycle/transcript metadata; raw audio only if separately authorized | Device/provider secrets outside events; no voice-only approval | Capture state, consent, classification, transcript minimization | Voice event correlation; stop/fail closed on permission or visibility uncertainty |

## Shared Failure Rule

Unknown identity, scope, visibility, destination, classification, integrity, or approval state denies or degrades safely. A lower-preference integration mechanism never expands authority. Core remains the control plane and UI projections never become trust anchors.
